DEV-1: Financial Schema and Payment Flow

GigResource, for PM and Owner review. September 18, 2026. Builds on the money ledger proposal (A1, Aug 22). Nothing in this document is built until it is approved; it unblocks G-1 to G-14.

In one paragraph. Every money movement is one row in an append-only ledger, and no total is ever stored and edited. A booking's price, what is held, what is owed to the professional and what GigResource earned are all sums over those rows. Payments move through one state machine (authorize, capture, hold, release, pay out), every step is idempotent, and the moment a payment is secured is a single database transaction that also authorizes the work. The payment schedule is a flexible, ordered list of stages set by the professional on their proposal, so G-14 needs no later migration.

1. Rules this design follows

  • Held until confirmed (D-5): client money is captured and held by the platform, and released to the professional only after the work is done and the dispute window has passed.
  • Append-only: corrections and refunds are new rows that reverse earlier rows by reference. Nothing financial is updated in place or deleted.
  • Totals are derived: there is no editable booking.total. Upgrades are separate line items that add to the client's running total (B3).
  • Commission on the service fee only: 5% Starter, 3% Pro, 1.5% Elite, taken at capture from the tier the professional holds at that moment (G-11). Never on reimbursements, taxes or the request fee.
  • $2.99 request fee: charged once at final submission, non-refundable in every case (D-3, G-13). Drafts are free.
  • Provider-agnostic: every provider reference is stored with the provider's name, so the D-11 choice (Stripe or Square) does not change the schema. Examples below use Stripe terms because every other record names Stripe.
  • Idempotent everywhere: every charge, webhook, expiry run and payout can be repeated safely (G-5, G-6).

2.6 reimbursements new (G-12)

Columns: booking_id, requested_by, description, amount, receipt_path, and state (submitted → approved / rejected → paid). An approved reimbursement becomes a reimbursement ledger row with no commission.

2.7 payout_items new and payouts change

payout_items links each payout to the release rows it pays, so every dollar sent can be traced back to a booking. To payouts add provider, provider_ref, idempotency_key and failure_reason, and the states pending → in_transit → paid / failed.

2.8 webhook_events new (G-4)

Columns: provider, provider_event_id (unique per provider), type, payload, signature_valid, received_at, processed_at, status, error. The handler checks the signature, stores the event and answers 2xx within 5 seconds; processing happens later on a queue. A repeated event id is acknowledged and ignored.

2.9 idempotency_keys new (G-5)

Columns: key (unique), scope, request_hash, response, locked_until, created_at. A second request with the same key gets the first response back instead of a second charge.

2.10 live_event_timeline_entries new (G-3)

An immutable, append-only record of what happened during a live event: check-in, upgrade requested, accepted, secured, applied, extended end time, and completion marked. Columns: booking_id, actor_id, kind, data (json), occurred_at. There is no update or delete path, and the model refuses both. Written under Owner hold B-3 only once it lifts.

3. Payment-state flow

3.1 The request fee (G-13, D-3)

Client presses Publish (final submission) → intent(purpose=request_fee, $2.99), idempotency key = request:{event_id} → authorize + capture at once → captured: ledger request_fee (+2.99, held→released to GigResource) request is published → failed: request stays a draft, client sees why, can retry No refund path exists for this fee (declined, withdrawn, expired alike).

3.2 A schedule stage: authorization, capture, hold

stage.scheduled ──(due rule reached)──▶ stage.due └─ intent created (key = stage:{stage_id}:{attempt_window}) requires_action ─▶ client completes 3-D Secure / confirms authorized ─▶ captured immediately (held-until-confirmed model) └─ PAYMENT SECURED transaction (3.3) failed ─▶ retry (3.4)

3.3 The Payment Secured transaction (G-1)

This runs once per captured intent, inside one database transaction. It is triggered by the webhook, or by the synchronous confirm, whichever arrives first. Both paths use the same idempotency key.

  1. Lock the intent row (SELECT … FOR UPDATE). If it is already captured, stop: this is a repeat.
  2. Set the intent to captured and the stage (or amendment) to secured.
  3. Write the ledger rows: stage_charge (or upgrade_charge) as held, commission at the tier rate on the service part only, and provider_fee.
  4. If this is the first stage required before work, set bookings.work_authorized_at.
  5. For an upgrade, set the amendment to applied, and extend new_end_at for time upgrades.
  6. Append a live_event_timeline_entries row where the booking is live.
  7. Commit, then queue notifications. Notifications are never sent inside the transaction, so a failure to notify cannot undo the money.

3.4 Retries and failure

failed (card declined / insufficient funds / requires new method) → attempts += 1, payment_attempts row written → retry at +1 day and +3 days (max 3 attempts), client notified each time → client may pay now with another method at any point (same stage, new key window) → after the last attempt: stage.failed deposit stage failed → agreement not funded; booking not confirmed later stage failed → booking flagged "payment overdue"; PM rule decides whether it cancels (see §6)

3.5 Expiry job (G-6)

A scheduled job runs every 5 minutes. It picks up expired authorizations, proposals past their deadline and amendments past respond_by (grace included), with SELECT … FOR UPDATE SKIP LOCKED. It moves each one to expired exactly once, so two workers or a rerun never double-process a row.

3.6 Release and payout

Work marked complete (both sides, or auto after the event) → dispute window runs (14 days, D-9) → no open dispute: held stage_charge / upgrade_charge rows get a release row payable = charges − commission − provider_fee + reimbursements → payout run groups release rows per professional (payout_items) key = payout:{professional}:{run_date} pending → in_transit → paid (failed → retried, then support) → open dispute: release waits; the dispute outcome writes release and/or refund rows

3.7 Refunds and cancellations

A refund never edits a charge. It writes refund rows that point, through reverses_id, at the exact rows they reverse. The amount comes from the cancellation tiers per booking (D-2), and a partial refund reverses part of a row. Commission on a refunded service amount is reversed with it. The $2.99 request fee is never refunded.

6. Decisions needed

  1. D-11 provider: Stripe or Square. The schema works with either; the webhook handler and the hold mechanism (Stripe Connect, or Square's equivalent) depend on it.
  2. Stage cap: 5 stages is proposed. Should there also be a minimum for the first stage (for example 10%)?
  3. Retry schedule: 3 attempts at +1 and +3 days is proposed. Also needed: what happens to a confirmed booking whose later stage fails for good (cancel it, or leave it flagged for the team)?
  4. Payout timing: release after the 14-day dispute window is proposed. Is there a payout schedule (weekly?) or a minimum amount?
  5. Taxes: record only in V1, or calculate and collect? Which states?

7. Build order once approved

  1. Ledger, intents, attempts, webhook events and idempotency keys, plus read helpers (owed, held, earned, paid).
  2. $2.99 at final submission (G-13), the smallest complete path end to end.
  3. Payment schedules on proposals (G-14) and stage payments with the Payment Secured transaction (G-1, G-2, G-11).
  4. Retries and the expiry job (G-5, G-6), then release, payouts and refunds.
  5. Amendments, the timeline and grace or extended time (G-3, G-7, G-9, G-10), once the Owner lifts B-3.

Existing screens keep working throughout: finance pages read from the ledger once it exists, and until then they keep showing N/A where there is no real data.
